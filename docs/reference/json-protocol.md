The JSON protocol is what a relay in front of a browser view speaks to that view: point operations on sessions, and
correlated streams that mirror a session's grid, search and capture it, wait on it, and relay notifications. Its types,
their conversions from and to the daemon wire's, and its correlation rules live in `felis-client-core::json` behind the
`json` feature, which builds for wasm32 without `native`. The transport and the host it routes to are the relay's: a
relay serving several daemons wraps each message in an envelope of its own, and nothing here names a host.

Every message is one JSON object whose `type` names it. The published schema is
`crates/felis-client-core/schemas/json-protocol-v1.schema.json`, regenerated by `just schema`; the golden messages under
`crates/felis-client-core/tests/golden/json-protocol/` are regenerated by `just golden`.

## Version negotiation

The client's first message offers every version it reads; the writer answers with the highest one both share, or refuses
and sends nothing more:

```json
{ "type": "hello", "versions": [1] }
{ "type": "welcome", "version": 1 }
{ "type": "refused", "versions": [1], "message": "..." }
```

`refused.versions` lists what the writer speaks. These three messages keep their shape in every version, so either side
reads them before a version is agreed. Every later message is spelled as the agreed version names it, and a writer sends
nothing that version does not name.

**Compatibility within a version.** Inside a version the only change a writer may make is adding an optional object
field. A reader ignores every property the schema does not name, and no object the schema publishes is closed.
Everything else is a new version: a new message, variant, item or enum value, a rename, a retype, or a field that
becomes required.

## Correlation and framing

A client names each request and stream with an `id`, a `u32` it picks and that is unique among what it has open. The
same key correlates both:

| Client message                      | Opens or acts on                                     |
| ----------------------------------- | ---------------------------------------------------- |
| `{"type":"request","id","request"}` | a request, answered once                             |
| `{"type":"open","id","stream"}`     | a stream                                             |
| `{"type":"input","id","input"}`     | the open `attach` stream `id` names                  |
| `{"type":"cancel","id"}`            | the open stream `id` names; its terminal still comes |

| Writer message                   | Meaning                                                               |
| -------------------------------- | --------------------------------------------------------------------- |
| `{"type":"reply","id","result"}` | a request's success; `result.op` names the operation                  |
| `{"type":"item","id","item"}`    | one stream item; `item.item` names it                                 |
| `{"type":"lag","id","dropped"}`  | `dropped` items were skipped and the stream goes on                   |
| `{"type":"end","id","count"}`    | the stream finished after `count` items, plus a capture's `exit_code` |
| `{"type":"error","id","error"}`  | the request or the stream failed                                      |
| `{"type":"lagged","id"}`         | the stream was cut off because its consumer fell behind               |

A request ends with exactly one `reply` or `error`. A stream ends with exactly one `end`, `error` or `lagged`, after its
items, and nothing names the id after it. `json::Ledger` holds these rules for one connection on either side.

`error` carries `{"kind", "message"}`. `kind` is one of `invalid_request`, `no_match`, `ambiguous`, `session_ended`,
`at_capacity`, `unsupported`, `refused`, `evicted`, `daemon_lost`, `internal`; `message` is prose and never parsed.

## Requests

| `request.op` | Fields                     | `result`                                  | Daemon request |
| ------------ | -------------------------- | ----------------------------------------- | -------------- |
| `list`       |                            | `{"op":"list","sessions":[session row…]}` | `Ops::List`    |
| `info`       | `session`                  | `{"op":"info","session":session row}`     | `Ops::Info`    |
| `create`     | `args`                     | `{"op":"create","session":session row}`   | `Ops::Spawn`   |
| `kill`       | `session`                  | `{"op":"kill","id"}`                      | `Ops::Destroy` |
| `tag`        | `session`, `add`, `remove` | `{"op":"tag","id","tags"}`                | `Ops::Tag`     |
| `send`       | `session`, `steps`         | `{"op":"send","id"}`                      | `Ops::Send`    |

`create` spawns a session nobody attaches to. A session row is the object `felis sessions info --format json` prints
([cli.md](cli.md) "Machine output") plus `sequence`, the daemon's creation order, which a tab bar sorts on since the
roster comes in recency order. `args` takes the daemon's spawn arguments, each key optional: `command`, `args`, `cwd`,
`env`, `dims`, `env_base`, `tags`. A send step is `{"step":"paste"|"raw","bytes"}`, `{"step":"key","event"}` or
`{"step":"mouse","event"}`; every step is written in order, or none is when one is refused.

## Streams

| `stream.stream` | Fields                                                    | Items                               | Daemon request               |
| --------------- | --------------------------------------------------------- | ----------------------------------- | ---------------------------- |
| `attach`        | `session`, or `create` with spawn `args`                  | `attached`, then `grid` and `image` | `Session::Attach` / `Create` |
| `wait`          | `session`, `steps` (may be empty)                         | `sent`, then `mark`                 | `Ops::SendAndWait`           |
| `search`        | `session`, `query`, `regex`, `case_insensitive`, `source` | `match`, newest line first          | `Search::Query`              |
| `capture`       | `session`, `source`, `ansi`, `max_rows`                   | `row`, oldest first                 | `Region::Rows`               |
| `notifications` | `session` (optional filter)                               | `notification`, with `lag`          | `Notify::Subscribe`          |

An `attach` stream's first item is `attached` whichever way it opened, carrying the session row and `minor`, the daemon
wire minor the stream speaks ([ipc.md](ipc.md) "Versioning"). A `create` whose stream cannot start leaves no session
behind. The client sends input on the stream's id; ending the stream detaches.

`grid`, `image` and `input` carry a frame of the matching wire family as a dedicated object tagged by `type`, one per
variant (`row_delta`, `cursor_state`, `placement`, `key`, `paste`, `resize`, `next_grid_frame` and the rest, as the
schema lists them). A `row_delta` row carries its cells as attribute runs over a grapheme list (`felis-grid::row_json`),
never the packed bytes the socket carries ([row-codec.md](row-codec.md)). The `CommandOutput` grid arm and the
`ViewportStep` and `AnnounceOutput` input arms are outside the protocol and are refused at conversion.

`search.source` is `scrollback` (the default) or `visible`; `capture.source` is `scrollback`, `visible`,
`command_output` or `last_command`. A `match` carries `anchor`, the history point its `line_index` and spans count from,
when the daemon reports one, so a scrollback hit stays addressable while output advances. A `wait` ends `session_ended`
when the session ends before its mark.

## Values

- A session id is its full 32-digit lowercase hex string, in requests and replies alike; no other spelling is read.
- Raw bytes (image chunks, clipboard writes, pastes, raw input, environment entries) are padded standard base64 strings.
- Every bitmap is an integer the schema bounds to the bits this build defines, so a reserved bit is refused rather than
  dropped.

What a reader refuses, the schema refuses with it, through the integer width of every numeric field, the printable-ASCII
window, the 1-based handles, the row codec's per-row caps, the function-key range, the session-id and base64 patterns,
and the OSC 66 ranges (the rule that a fraction stays below its denominator rides one `if`/`then` per denominator). Two
checks surface only as a refusal at conversion: the attribute runs covering exactly the row's graphemes, and a sized
cell naming a column the row has. A `u64` bound carries `x-bound-exceeds-f64-precision`, because a validator comparing
JSON numbers as `f64` enforces that bound rounded.
